# Post-Competition Audit — July 2026

Full-codebase audit after the April 2026 competition push (the hack burst is
April 18–19; the er-force friendly follow-ups landed May 25). The separate
pre-competition **Gui** audit (July 8) was re-verified — all findings still
current — and is absorbed here as section G, keeping its original item IDs.

Each item has an effort estimate (S = under an hour, M = a session,
L = multiple sessions) and a risk level (how likely the change is to break
behavior that matters). Status legend: `[ ]` todo · `[x]` done ·
`[-]` rejected/deferred.

**Overall picture:** the foundations are in good shape — `Common` (math,
dataflow, config, debug-db), `Vision`, and the role-assignment solver are
well-engineered and mostly well-tested. The debt is concentrated in three
places: (1) the **command/kick unit chain** and the ZMQ sender, which is
carrying deliberate protocol hacks; (2) the **Soccer tactics layer**
(BallPlacement, plays, obstacles), which has real bugs and dead code from the
competition push; (3) the **test suite, which has been red since April** —
9 failures that nobody reconciled with the behavior changes that caused them.

## U. Command / kick unit chain (highest-priority correctness debt)

### U1. `Command.Shoot`/`Chip` have no defined unit or meaning — `[ ]` (L, high risk — needs robot/sim testing)
The same two floats mean different things depending on who wrote them and who
reads them:

- AI writes **mm/s**: `Knowledge.AttackerDecision.cs:9` (`AttackerKickSpeed =
  6500`), `PassChipSpeed = 2000`
- Manual control writes **m/s** and **meters**: `ManualControl.cs:71-72`
  (`_kickSpeedMps = 6f`, `_chipDistanceMeters = 4f`) feed the same
  `KickBall.Kick`/`Chip` properties
- `Knowledge.AttackerDecision.cs:216` uses `kick = 1.0f` as a magic
  "approach but don't kick" sentinel
- `Sender/Simulator.cs:53-61` forwards `command.Shoot` **unconverted** to the
  sim protocol's `KickSpeed` (which expects m/s) and sends `command.Chip * 5`
- `Sender/ZmqRobotSender.cs:88-93` (commit `b5bf55e`, "Fix zmq protocol, in a
  hacky way") is the worst of it — the fields are **swapped** with magic
  factors, and the shoot-calibration path was deleted:
  ```csharp
  Vx = cmd.Motion.X * 1.2f / 1000.0f,   // 1.2 velocity fudge factor
  Chip  = cmd.Shoot * 0.7f / 1000.0f,   // shoot power sent on the chip field
  Shoot = cmd is { Chip: > 10, Shoot: 0 } ? 5.0f : 0.0f,
  ```

**Fix:** define the contract once on `Common/Sender/Data/Command.cs` — e.g.
`KickSpeed` [mm/s] and `ChipDistance` [mm], per the repo convention — then
make every producer (KickBall/OneTouch/TurnAndShoot/CircleBall via
AttackerDecision, ManualControl) and every consumer (Simulator, Zmq, Nrf)
honor it. If the 1.2/0.7 factors and the field swap compensate for real
firmware behavior, they belong in the firmware or in an explicit, per-robot
calibration table (`ShootCalibration` exists for exactly this and is now only
used by the untested `Nrf` path — `Sender/Nrf.cs:9` "untested, test at the
competition"). Replace the `kick = 1.0f` sentinel with an explicit
`Kick = 0` / `bool Approach` signal. This item needs bench time with a real
robot; until then at least document the current semantics next to the code.

### U2. Collision-imminent braking disabled but still computed — `[-]` kept as dev toggle 2026-09-04 (S–M, medium risk)

> **History check:** `2d78c4e` (2026-04-18) only wrapped the four lines in
> `//` and nothing replaced the braking; the commit message's "(Should be
> changed)" is an explicit revisit marker. Left intact so re-enabling is a
> one-line uncomment. Still open: retune or redesign (needs a sim session).
Commit `2d78c4e` ("Remove collisionImminent (Should be changed)") commented
out the emergency-stop response in `Soccer/Robot/Robot.Navigation.cs:132-137`,
but the `_obsMap.HasCollision(...)` query at `:129` still runs every tick per
robot and its result is discarded. Either the safety behavior was bad (then
delete the whole block and the wasted query) or it needs retuning (then
retune it) — the commit message itself says "Should be changed". Decide and
do; don't leave a disabled safety feature as commented-out code.

### U3. `Filter2D.GetPosition` band-aid — `[ ]` (S, low risk)
`Vision/Filter/Filter2D.cs:117-122` (commit `8e73982`): extrapolation is
silently disabled for |dt| > 1 s. Probably a reasonable guard against stale
trackers, but it was added mid-competition, it broke its own unit test (T1),
the cutoff is a magic constant, and returning the raw position with no
indication is a silent behavior cliff. Make the threshold a `[ConfigEntry]`,
decide the intended semantics, and fix the test to match.

### S2. `BallPlacement` — bugs and dead code — `[x]` fixed 2026-09-04 (M, medium risk)

> **Resolution:** NRE guarded (placers missing → halt), `KissTouch` state and
> the `if (false)` branch deleted, `Done → Idle` reduced to the ball-drifted
> clause (the second clause was redundant, not inverted — see
> `AUDIT-2026-09.md`), `Timestamp.Now` → `Context.Time`, commented-out lines
> removed, and the placer final positions are now nullable with a retreat
> fallback so a tactic that starts with the ball already placed no longer
> drives both placers to the field centre. Magic distances are still inline
> (tracked as NS15 in the September doc).
`Soccer/Tactics/BallPlacement.cs` was the ball-placement rewrite under
pressure (`01cda4d` → `10da2f1` → `1f3d9b3` → `351cd60`) and it shows:

- **NRE waiting to happen:** `KissingState.Tick` (`:314`) dereferences
  `ballPlacer1.Position` / `ballPlacer2.Position` *before* the null check at
  `:316`. If a placer robot drops off vision mid-state, the AI tick throws.
- **Dead branch:** `StuckState.Tick` (`:368`) — `if (false && timeInState...)`
  with the live else-branch. Delete or restore.
- **Unreachable state:** no transition targets `State.KissTouch`
  (only *from* it, `:80-81`), so `KissTouchState` is dead code.
- **Unparseable transition:** the `Done → Idle` condition (`:120-123`) mixes
  `||`/`&&` across four lines without parentheses; as written, "both placers
  reached their final positions" forces a return to Idle, which looks
  inverted. Decide the intent and write it as named booleans.
- **Wall-clock leak:** `:117` uses `Timestamp.Now` where every other tactic
  uses `Context.Time` — breaks determinism under replay/log-driven testing.
- Commented-out lines (`:318`, `:327`) and unexplained magic distances
  (75/20/100/150/4000 mm) throughout.

### S3. `Zone` scoring — side-dependency bug + copy-paste — `[ ]` (M, medium risk)
`Soccer/Knowledge/Zone.cs`:

- **Side bug:** `:38` excludes kickoff zones with `Rect.Center.X < 0f`, but
  coordinates are *not* side-normalized (`FieldSizeExtensions.OwnGoal()` uses
  `Context.SideSign`) — so this is only correct when we play on the right.
  On the left half it excludes *our own* half instead. Use
  `Context.Field.TheirHalf()` / `SideSign`.
- `CalculateScoreDefense` (`:76`) and `CalculateScoreOffense` (`:134`) are
  ~90 % identical; variable names (`oppDisToGoal`, `oppToBall`) were copied
  from opponent-threat code and describe the wrong thing. Extract one scoring
  function parameterized by goal, and hoist the tuning constants
  (3000/6000/400/15/0.85) into `[ConfigEntry]`s.
- `UpdateZones` (`Knowledge.Zone.cs`) allocates all zone objects and
  re-sorts twice per tick, and `zone.DrawZone()` renders a filled rect per
  zone per tick unconditionally. Cheap wins: reuse the zone grid, draw only
  under a debug layer toggle.

### S4. Obstacle map assembly — likely bug + per-tick garbage — `[ ]` (M, medium risk)
`Soccer/Robot/Robot.Obstacles.cs`:

- **Likely copy-paste bug (verify on sim):** `:60` sizes *teammate* obstacles
  with `CalculateRobotRadius(State)` — `State` is **self**, so a teammate's
  obstacle radius grows with *my* speed, not theirs. The opponent loop
  (`:68`) does it right (`CalculateOtherRadius(State, opp.State)`).
  Presumably intended: `CalculateRobotRadius(own.State)`, or a symmetric
  `CalculateOtherRadius` treatment.
- `SetObstacles` runs per robot per tick and allocates the goal-post /
  wall rectangles as fresh arrays each time (`:102`, `:122`, `:146`). The
  field geometry only changes on `FieldSize` updates — build these once and
  cache.
- Ball-radius flag tiers embed magic radii inline (`230.0f`, `60.0f`,
  `:79-80`) next to configurable ones — promote to `[ConfigEntry]` alongside
  `BallAreaRadius`.
- Every `Map.Add` also emits debug draws (`Map.cs:42-49`), so with 11 robots
  the full obstacle set is drawn 11× per frame into the Obstacles layer.
  Draw once per tick (or per selected robot), not per map instance.

### S5. `PlayBook` — reflection priority roulette — `[ ]` (M, low risk)
`Soccer/Plays/PlayBook.cs`: play priority is the order `Assembly.GetTypes()`
happens to return (the doc comment even admits callers "should order by
priority if needed" — nothing does). `NormalPlay.IsApplicable()`
(`Referee.Running()`) can shadow or be shadowed by other applicable plays
depending on the compiler's type-emission order. Also `FindApplicable()` does
a reflection `MethodInfo.Invoke` per play and `Activator.CreateInstance` for
the winner **every tick** (`Ai.cs:167`), so plays can never hold state across
ticks — fine today (all plays are stateless), but it's an invisible trap.
**Fix:** an explicit ordered list (or a `[Play(priority: …)]` attribute),
instantiate once, reuse instances, and make `IsApplicable` an instance method
so the reflection goes away.

## D. Debug tooling (`Common/Debug`)

Overall verdict: this is the strongest part of the codebase — the
memory-mapped DebugDb, sharded buckets, caller-info-capturing draw API, and
packed `PlotValue` are genuinely good. Three real issues:

### D1. `Drawer` is not thread-safe but is shared by both team threads — `[x]` fixed 2026-09-04 (M, medium risk)

> **Resolution:** premise corrected in `AUDIT-2026-09.md` (the sharing is
> between the per-robot navigation tasks of one team, not Yellow/Blue).
> `MakeExpression` now builds into a pooled per-call `ZString` builder; the
> shared `_stringBuilder`, the per-Drawer cache and `IDisposable` are gone.
> `_layer` is still per-instance state — documented on the class.
`Common/Debug/Drawing/Drawer.cs:20` — one `Drawer` exists per *module*
(`Registry.GetDrawer(ModuleName)` via the generated globals), but the Soccer
module runs two AI threads (Yellow + Blue). `_stringBuilder` (a mutable
`Utf16ValueStringBuilder` struct field) is Clear()ed and appended without
synchronization in `MakeExpression` — concurrent draws from both teams race
and can corrupt expression strings or throw. Rarely seen because we usually
run one team, which makes it worse when it finally fires at a two-team test.
**Fix:** make `_stringBuilder` `[ThreadStatic]` (like `DebugDb`'s
`_serializeBuffer`) or per-call.

### D2. `InternExpression` trusts a 32-bit hash — `[x]` fixed 2026-09-04 (S, low risk)

> **Resolution:** the same hash-only pattern had spread to the global
> `InternedStringCache` (plot ids *and* every log message). It is now one
> content-keyed `ConcurrentDictionary<string,string>` with a span alternate
> lookup (still allocation-free on hit); `Drawer` and `Plotter` both use it.
`Drawer.cs:23-30` caches interned expression strings keyed **only** by
`string.GetHashCode(span)` — a hash collision silently returns the wrong
expression label for a drawable. Cheap fix: key by the actual string (the
allocation only happens on cache miss anyway).

### D3. `ServiceLocator` — `[ ]` (S–M, low risk)
`Common/ServiceLocator.cs` is a one-field global (`BallTrajectoryFactory`,
`null!` until Vision's module initializer runs) consumed deep inside Soccer
skills (`InterceptV2.cs:117`). It works, but it's an invisible init-order
dependency — Soccer explodes if vision isn't loaded. Either move the factory
interface + default implementation into `Common` proper, or inject it via
`Knowledge`/`Context` where the other cross-module state already lives.

(The GUI-side debug-tooling issues — DebugFilter tree, LogView twins,
playback-border/search-bar duplication, journal-grouping config read from a
view — are tracked as G.C2/C3/C5 and G.A5 below.)

## G. Gui project (absorbed from the July 8 GUI audit)

The guiding rule for all GUI work:

> **The GUI operates on either the live or the replayed state of the world,
> selected by the playback control.** A panel showing internals of a core
> module must get that data through the debug-db / playback pathway — never
> by reading module state directly.

## P. Process findings (from the git history)

  ("temp", "Desired", "bp", "f2d", "kickoff test"). Fine mid-match; the
  problem is they're indistinguishable from intentional changes three months

  convention for tournament hacks: prefix `HACK:` in the subject and/or a
  `// HACK(comp2026):` comment at the site. Then a post-competition sweep is
  a grep, not an archaeology dig.

  has failed on every main push since April 19 with exactly the T1 tests.
  The fix is visibility, not tooling: branch protection on main requiring
  the workflow, and/or failure notifications. (The bot PRs from "Bolt" have
  also been failing against the broken baseline the whole time.)

  checkboxes in place, in the same commit as the fix they describe.

  `Sender/ShootCalibration.cs:6` says "doesn't belong here, move to Soccer".
